# PERF.md —— 渲染要多久、瓶颈在哪、怎么加快（实测数据）

> **A1 · 草稿档 `--draft`（2026-10-25）**：半分辨率（960×540）+ `samples=1`。同一台机器、
> `_calib --from 0 --to 1`（60 帧，`samples=1`）：**1080p 13.5 fps / 4.4s → 540p 33.5 fps / 1.8s = 2.5×**。
> 这是 `samples=1` 的对照；真片子走 `auto` 时（静止画面加到 8+ 子帧），差距会是 **8–24×**。
> 用途只有一个 —— 审节奏与信息密度（BACKLOG 1-44），**不是成片**。
> **2026-10-31 深夜（C-1）**：`video --dry-run` 现在会真测草稿档与成片档各 10 帧、分别报分钟数。
> 同轮把默认审片命令定为 `video <任务> --draft --segments 10`：用户明确确认后才去掉 `--draft` 出正式版。

> 起因：`tasks/beast` 第二版 127.5 秒 = 7650 帧，串行渲要一个小时。这份文档把
> 「时间花在哪」量清楚，并给出可复制的加速做法与验收口径。
> **所有数字都是本机实测**（AMD Ryzen 7 5800H / 8 核 16 线程、AMD Radeon 核显 + RTX 3070 Laptop、
> Windows、Chrome 无头、1920×1080、带胶片颗粒）。换机器请重测，别照搬结论。
>
> **2026-10 更新（第二轮）**：第一轮的瓶颈（`readPixels`）已经修掉，端到端 **3.8 → 7.5 fps**；
> 新瓶颈换成了**把裸帧搬出浏览器**。§2① 关于独显的旧结论也**已作废**（重测反超 2.15×）。
> 新增的实测都在 §5。

## 1. 结论先行

> **第一轮（2026-10 之前）：瓶颈是浏览器那一侧的「整帧回读 `readPixels`」**，不是编码器、不是磁盘、
> 也不是显卡不够强。它的根因不是 GPU，而是 **JS 侧每帧 `new` 一个 33MB 的 Float32Array**
> （1080p/4K 的 RGBA16F 读回中转）+ 8.3MB 的结果数组，再叠上逐通道 `Math.pow` 编码。
>
> **第二轮（现在）：`readPixels` 从 195ms → 6.4ms（30×），端到端 3.8 → 7.5 fps。**
> 新瓶颈是 **Chrome → Node 的 WebSocket 传输（实测 ~110 MB/s ⇒ 8.3MB/帧要 72ms）**，
> 而 ffmpeg 那一侧只要 4.2ms/帧。见 §5.3：接下来要么少传字节（YUV420 / 浏览器内编码），
> 要么换通道。

**历史数字（第一轮，`samples=8`、300 帧，仍然成立的部分）**：

| 环节 | 实测 | 折算 |
|---|---|---|
| 浏览器渲 1 帧（`--samples 1`） | **214 ms** | 4.7 fps |
| 每多一个运动模糊子帧 | **+29 ms** | 子帧很便宜 |
| 浏览器渲 1 帧（`--samples 8`） | **420 ms** | 2.4 fps ← 当时的天花板 |
| `libx264 -preset slow -crf 16` | 85 ms | 11.8 fps |
| `libx264 -preset medium -crf 18` | 38 ms | 26 fps |
| `libx264 -preset veryfast -crf 18` | 15 ms | 67 fps |
| `h264_nvenc -preset p5 -cq 19` | **5.4 ms** | 166–185 fps |
| 端到端（samples=8 + x264） | 465 ms/帧 | 2.15 fps（天花板的 90%） |
| 端到端（samples=8 + nvenc） | 461 ms/帧 | 2.17 fps（同上，编码被完全隐藏） |

复现命令（300 帧，测编码器本身；`decode-only` 是解码基线）：

```sh
ffmpeg -benchmark -v error -i 成片.mp4 -frames:v 300 -c:v libx264 -preset slow -crf 16 -f null -
ffmpeg -benchmark -v error -i 成片.mp4 -frames:v 300 -c:v h264_nvenc -preset p5 -cq 19 -f null -
node scripts/anim.mjs perf <任务> --from 40 --to 44 --samples 1     # 浏览器那一侧
node scripts/anim.mjs perf <任务> --from 40 --to 44 --samples 8
```

## 2. 三个反直觉的实测结论

### ① 独显 vs 核显：**旧结论已作废，必须重测**（2026-10 重测：raymarch 段独显反超 2.15×）

> 旧的结论是「不要加 `--force_high_performance_gpu`，独显更慢」（核显 420ms/帧 vs 独显 520ms）。
> **那条是在 readPixels 要 195ms/帧 的年代量的** —— 当时的成本大头正是「整帧回读 + 跨适配器拷贝」，
> 跟填充率没关系。现在读回只要 ~6ms（§5.1），`readPixels` 修好之后**重测**（同一台机器、同一个
> promo、1080p、`samples=1`、连续 40 帧「渲染 + 读回」）：

| 场景 | 核显（默认） | RTX 3070（`--force_high_performance_gpu`） | 结论 |
|---|---|---|---|
| raymarch 大厅段（t=21） | 125.4 ms/帧 | **58.3 ms/帧** | **2.15× 更快** |
| 走廊段（t=10，轻） | 45.0 ms/帧 | 51.4 ms/帧 | 慢 14%（付跨适配器拷贝的钱） |
| CLI 口径（`anim perf promo --from 21 --to 22`） | 144.1 ms | 76.2 ms | 1.89× |

**规则：GPU 填充越重，独显越划算；轻场景付跨适配器拷贝的钱。** 所以引擎不替你预设 ——
用 `--gpu high` 显式开，拿不准就先 `node scripts/anim.mjs perf <任务> --gpu high` 量一段。
（`scripts/anim.mjs` 的 Chrome 启动参数里保留了这段注释。）

复现：`node out/_probe/perf-breakdown.mjs promo 21` 与 `... promo 21 --force-gpu`。

### ② 并行渲不同区间：⚠ **历史结论，已不是首选**
> **先读这条**：下表是「`readPixels` 修好之前、一个进程吃不满机器」那个年代的数字。
> NV12 之后实测 4 进程 720 帧 ≈ 6.1 fps，**比单进程 7.5 fps 还慢**（多进程互相抢核显与 ws 带宽，见 §5.6 第 6 条）。
> 要用就先 `anim perf` 量一段。另外 `--parallel` 有两个副作用：它**静默忽略 `--segments`**
> （CLI 里 `--parallel` 的分支在 `--segments` 之前 return），而且只转发
> `--vcodec/--crf/--cq/--preset/--x264/--scale/--tol/--gpu`（`--idle/--force/--keep-raw/--only` 都不生效）。
>
> 又稳又快的默认选择是 **`--segments`**（断点续渲，切点只落在镜头边界）+ `--gpu high`。

浏览器一侧只吃一核 JS + 一份 GPU，第二个/第三个进程能填上空档。当年的实测（300 帧，samples=8）：

| 方式 | 总墙钟 | 加速 |
|---|---|---|
| 串行 1 个进程 | 139.4 s | 1.00× |
| **2 个进程并行**（各 150 帧） | **76.9 s** | **1.81×** |
| **3 个进程并行**（本片 7650 帧的实战） | 26.1 min（串行预估 59 min） | **2.3×** |

实战做法（本片的命令，注意切点）：

```sh
# 切点只能落在「下一段转场已经结束」的时刻（否则这一段开头拿不到上一帧，甩镜会缺一半）
node scripts/anim.mjs video <任务> --from 0   --to 40    --samples 8 --vcodec h264_nvenc --cq 19 --out out/<任务>/part1.mp4
node scripts/anim.mjs video <任务> --from 40  --to 85    --samples 8 --vcodec h264_nvenc --cq 19 --out out/<任务>/part2.mp4
node scripts/anim.mjs video <任务> --from 85  --to 127.5 --samples 8 --vcodec h264_nvenc --cq 19 --out out/<任务>/part3.mp4
# 拼接：⚠ 必须带 -copyts（见第 4 节）
ffmpeg -copyts -f concat -safe 0 -i concat.txt -i audio/beast-vo.m4a -map 0:v -map 1:a -c copy -movflags +faststart beast.mp4
```

占用提醒：3 个 ffmpeg 各约 2 GB 工作集 + 3 个 Chrome，本机 32 GB 内存只剩 0.7 GB，会明显变慢。
内存紧就降到 2 个进程。

### ③ 子帧是线性成本，编码器不是
`--samples 8 → 4` 大约省 25% 墙钟（-116 ms/帧），代价是运动模糊颗粒变粗。
反过来，如果内容以静止为主，提高 samples 几乎不要钱（+29 ms/子帧），而编码器早已被隐藏 ——
所以**降 samples 换时间，比压缩编码器设置划算得多**。

> ⚠ **但它不是第一顺位**：这是整份文档里唯一会**直接让画面变差**的一刀。提速按"损不损画面"排序：
> 1. **`--gpu high`**（填充重的段实测 **2.15×**，逐像素不变；轻场景反而慢 14%，所以先
>    `node scripts/anim.mjs perf <任务> --gpu high` 量一段）；
> 2. **`--segments N`** —— 它的价值是**断点续渲**（改一个镜头不用整片重来），**不是提速**；
> 3. 再往下才是 **`--samples 8`**：把自适应（8→24→72→216）**固定**成 8 个子帧。
>    注意 `--samples 4` 会被引擎**夹回 8**（`src/core/engine.js` 的 `BASE_SAMPLES = 8`），写 8 语义更干净；
>    反过来 —— **想让甩镜/快速运镜的拖影更细，该调小 `--tol`（默认 2.5），不是加 `--samples`**；
> 4. 最后才考虑降分辨率（`--scale`）：那是硬降分辨率，别用。

## 3. `--vcodec`：新加的硬件编码开关

原来 CLI 写死 `libx264`。现在：

```sh
--vcodec h264_nvenc --cq 19        # 硬件编码；质量用 --cq 控，速度用 --preset p1..p7
--vcodec libx264 --crf 16 --preset slow   # 默认，质量最好
```

它在本机不省端到端时间（渲染是瓶颈），但**把 16 个 CPU 线程全让给浏览器那一侧**，
在子帧少、渲染快、或同时跑多个进程时是净赚；另外它让「编码」这一环从 CPU 上消失，
机器不会因为 x264 吃满而影响其他工作。

## 4. 验收口径的三个坑（都踩过，都实测过）

### ① 自己拼接分块时必须 `-copyts`
不带 `-copyts` 时，concat 会把整条视频的时间戳推后 **+0.022982 s**（B 帧的 CTS 偏移，
首帧 PTS 从 0.000000 变成 0.022982）。后果：**帧号与时间戳不再对齐**，
「按时间抽帧」会抽到相邻帧 —— 表现为「内容对得上、颗粒图案不同」（mean≈10、超阈值像素 25%）。
带上 `-copyts` 后首帧 PTS = 0.000000、帧距 1/60，帧号与时间戳重新对齐。

### ② 「同参数渲两遍」是逐比特相同的，但「从不同起点开渲」不是
- `video --from 110 --to 112` 跑两遍：**PSNR = inf**（逐比特相同，连文件大小都一样）。
- 成片（part3 从 85s 起渲）vs 从 110s 起渲的同一窗口：**PSNR ≈ 34.8 dB**（肉眼不可见，颗粒级）。
- 从 105s 起渲（预热 5s）也一样 ≈ 33.2 dB，所以**不是简单的"预热"问题**。

**结论**：引擎的确定性是「同一会话起点下」的确定性。因此
`verify`（单帧重渲 vs 成片抽帧）在本片上只能部分通过 —— 那不是成片错了，
而是参考帧与成片不是同一条渲染路径。**有意义的验收是**：
① 帧数 = 时长 × fps；② 成片与自己分块的拼接 **PSNR = inf**；
③ 同窗口同起点的重渲 **PSNR = inf**；④ 抽帧看图。

### ③ `verify` 的取时口径在帧边界上不稳
引擎算帧号是 `idx = floor(t*fps + 1e-6)`，而 `verify` 的探针写成 6 位小数：
`t = 6.133333` → `6.133333*60 = 367.99998` → `idx = 367`，而成片那一帧是 368 —— 差一帧，
颗粒图案就不同（mean≈10）。**探针要抬到帧内一点点**（`+0.0005`），并且抽帧窗口
（`between(t, t±半帧)`）在帧边界上是闭区间，会同时框住前后两帧。
最稳的做法是直接用「帧号」比对（`select=eq(n\,N)`）而不是「按时间抽帧」。

## 5. 第二轮实测（2026-10）：`readPixels` 修好之后，瓶颈换了位置

### 5.1 根因：不是 GPU、不是 `pow`，是**每帧 new 33MB**

`gl.readPixels()` 之前每帧都 `new Float32Array(1080p×4)`（**33MB**）+ `new Uint8Array`（8.3MB），
再逐通道 `Math.round(sat(linearToSrgb(v))*255)`。1080p 全帧、同一会话同一帧、取 5 次中位数：

| 实现 | 耗时 | 相对 |
|---|---|---|
| 旧：每帧分配 + 逐通道 `Math.pow` | **195.0 ms** | 1.0× |
| 每帧分配 + 直算（把循环写成 JIT 友好的形式） | 17.1 ms | 11.4× |
| **复用缓冲 + 直算（现在默认，逐像素等价）** | **6.4 ms** | **30.5×** |
| 复用缓冲 + sRGB 查表（256 项） | 7.9 ms | 24.7× |
| GPU blit 编码 + 8bit 回读（另一条路） | 5.2 ms | 37.5× |

分解（同一帧）：纯 `GL.readPixels(FLOAT)` 只要 **0.1–0.2 ms**、`'none'`（读回 + 简单 8bit 量化）
5.9 ms，而 `'srgb'`（多一步编码）**142–197 ms**。所以「GPU 回读」从来不是问题，**分配 + 编码循环是**。

修法（`src/core/gl.js`）：**GL 实例持有读回缓冲并复用**，热循环拆开 `encode` 分支、用局部变量
（`this._px*` 会让 V8 的类型反馈带上 Nullable，循环跑不进最快档）。
**数学一个字没改** ⇒ 画面逐像素不变，已用基线机械证明：

```sh
node scripts/anim.mjs hashes promo --baseline    # 4 帧
node scripts/anim.mjs hashes demo  --baseline    # 11 帧
node scripts/anim.mjs hashes beat  --baseline    # 11 帧
node scripts/anim.mjs hashes fidus --baseline    # 4 帧
# 全部 max 0 / mean 0.0000（30 帧，逐像素完全一致）
```

⚠ **语义变化**：`readPixels()` 返回的是**内部缓冲**，下一次读回会覆盖它。
需要留存就 `new Uint8Array(buf)` 或传 `{ copy: true }`（跨 `await` 的两帧比较必须复制，
`app.js` 的 `diff()` 已这么写）。量具与证据：`out/_probe/srgb-lut-check.mjs`、`out/_probe/perf-breakdown.mjs`。

> 顺带：sRGB 那一步用 **256 项查表**也能快 2.3×，但**默认没用它** —— 复用缓冲之后 `pow`
> 已经不是瓶颈（6.4 vs 7.9ms，查表的随机访问反而更慢），而**不改数学**才能保证基线不用重存。

### 5.2 端到端（同一命令、同一任务、同一台机器）

| 口径 | 旧 | 新 | 倍数 |
|---|---|---|---|
| `anim perf promo --from 10 --to 12 --samples 1` | 215.6 ms/帧 | **66.7 ms/帧** | 3.2× |
| `anim shot promo --from 10 --to 16 --samples 1`（真实出片，360 帧） | 95.7 s（3.8 fps） | **47.9 s（7.5 fps）** | **1.97×** |
| 同上，但 `--vcodec h264_nvenc` | — | 46.3 s（7.8 fps） | 编码器**不是**瓶颈 |
| **同一条命令，NV12 推流之后**（§5.4a，2026-10） | 47.9 s（7.5 fps） | **29.3 s（12.3 fps）** | **1.63×** |
| `anim video _calib --from 0 --to 12 --samples 1`（720 帧），**R8/RG8 回读之后**（§5.4a，2026-10-17） | 47.8 s（**15.1 fps** / 66.4 ms/帧） | **44.5 s（16.2 fps / 61.8 ms/帧）**；三次 44.3–44.6 s | **1.07×** |

### 5.3 新瓶颈：把裸帧搬出浏览器（~110 MB/s）

出片是「页面渲染 → WebSocket 推 8.3MB/帧 → Node `ff.stdin.write()` → ffmpeg」。
`readPixels` 提速后，每帧还剩 ~126ms 花在渲染之外，而 **ffmpeg 那一侧只要 4.2ms/帧**
（`out/_probe/pipe-cost.mjs`：当前参数 vflip+bt709+x264 veryfast = 237 fps；去掉滤镜 4.1ms；
NVENC 5.7ms；只收不编 2.1ms）。所以差额全在**传输**：

> ⚠ 下表量的是 **RGBA 那版**（8.3MB/帧）。2026-10 起推的是 **NV12**（3.11MB/帧，§5.4a）——
> 表里的"通道天花板"结论仍然成立，只是每帧成本按 3/8 折算（72–79ms → ~28ms）。

| 通道（7.91MB/帧） | 吞吐 | 每帧 | 备注 |
|---|---|---|---|
| ① WebSocket 二进制（现状） | 101–115 MB/s | 72–79 ms | Chrome→Node |
| ② HTTP POST（一帧一请求） | 24–26 MB/s | 304–327 ms | 每请求固定开销太大 |
| ④ 攒 8 帧一次 `ws.send` | 103–115 MB/s | 69–75 ms | 只快 1.01–1.11× ⇒ **不是消息数的问题** |
| ⑤ `fetch` 流式上传（1 请求 N 帧） | — | — | 本机被挡：`ERR_ALPN_NEGOTIATION_FAILED`（未取到数） |
| ⑥ Node→Node 的 ws（`out/_probe/ws-cpu.mjs`） | **245 MB/s** | 32 ms | 排除 Chrome 之后的上限 |
| 纯内存拷贝（下限） | 2.3–2.6 GB/s | 3.0–3.4 ms | |

**结论**：`ws` 这条通道的天花板就是 ~110 MB/s，攒帧也救不了（④）。而且即便优化到 Node→Node
那个 245 MB/s，8.3MB/帧仍要 32ms。**唯一出路是少传字节**。

### 5.4 少传字节：**NV12 传输（已落地，2026-10）**

**(a) YUV420 / NV12 —— ✅ 已落地**（这是本节原来"已量过、未落地"的那一条）。

做法：GPU 上加两个全屏 pass（`src/core/gl.js` 的 `readNV12()`）—— 一个出 Y 平面（全分辨率）、
一个出**交错 UV** 平面（半分辨率，2×2 盒式平均），公式就是 swscale 那套
（全范围 sRGB → BT.709 limited）。回读 3.11MB/帧 而不是 8.3MB，推流照旧走 ws；
ffmpeg 那侧改成 `-pix_fmt nv12` 直接吃，**不再做 RGB→YUV 转换**
（只剩 `vflip` + 4K 时的 `scale`，并钉住 `range=limited` 的色彩标记）。

| 量 | 结果 |
|---|---|
| 每帧字节 | 8.29MB → **3.11MB（−62%）** |
| 回读字节（2026-10-17，R8/RG8 之后） | **10.37MB/帧（Y 按 RGBA 8.29 + UV 2.07）→ 3.11MB/帧（R8 2.07 + RG8 1.04）＝ −70%**；CPU 紧凑化循环整个删掉（原 `gl.js:676-677` 的两行 for） |
| 传输（按 §5.3 的 ~110MB/s 实测） | 72–79ms → **~28ms** |
| 画质 | 成片本来就是 `yuv420p`：这不是新增一次色度损失，只是把同一个 4:2:0 转换从 swscale 挪到 GPU。**唯一变化是色度下采样的滤波器核**（盒式平均 vs bicubic） |
| 端到端（实测） | `anim shot promo --from 10 --to 16 --samples 1`（360 帧，**§5.2 那条基准命令**）：47.9s（7.5 fps）→ **29.3s（12.3 fps）= 1.63×**；`anim video _calib --from 0 --to 12 --samples 1`：720 帧 / 51.7s = 13.9 fps |
| 正确性 | `tools/probe-nv12.mjs` GPU 的 NV12 vs CPU 参考实现：**max 1 码值、>1 占 0.00%**；`anim verify _calib` → **8/8 时刻一致**（mean 0.00–3.19，判据 <18）；同一静态帧**两次独立会话出的成片逐字节相同**；与旧路径（交付版 promo）同帧对照：三个平面的**有符号均值 ≤0.08 码值**（无偏色），Y/U/V 的平均差 1.72 / 0.79 / 0.85（编码噪声级） |
| 端到端（R8/RG8 之后，2026-10-17） | `anim video _calib --from 0 --to 12 --samples 1`（720 帧）：**47.8s（15.1 fps / 66.4 ms）→ 44.5s（16.2 fps / 61.8 ms）= 1.07×**（背靠背 A/B：旧实现 `git stash` 后先跑一次；新实现连跑三次 44.3–44.6s）。省下约 **4.6ms/帧**，与「回读少 7.26MB + 少 259 万次紧凑化循环」的预估（~6ms）同量级；上面那行 51.7s/13.9 fps 是同一条命令的另一次旧测 |

> ⚠ 老片子（nekohome / fidus / beast / promo / demo / beat）已经用旧路径出过片，**不会**因此改变；
> `hashes` 基线量的是**渲染结果**（浏览器侧），也不受影响。改的是"以后出片"的那条路。

**(b) 浏览器内编码（WebCodecs，实测可行、未落地）**——传输量直接消失：

| 编码 | 每帧耗时 | 每帧字节 | 比裸 RGBA 小 |
|---|---|---|---|
| H.264 `avc1.4d002a`（`latencyMode:'quality'`, 12Mbps） | 38.7 ms | **27 KB** | **314×** |
| H.264 `hardwareAcceleration:'prefer-hardware'` | 38.9 ms | 27 KB | 314× |
| VP9 | 41.1 ms | 29 KB | 294× |
| （对照）deflate 压裸帧 | **339 ms** | 1.54 MB | 5.2× ← 不划算 |

`VideoEncoder` 在无头 Chrome 里**可用**（`avc1.42E01E` 不支持，用 `avc1.4d002a`）。
代价：①编码 38.7ms/帧本身要算进去；②要放弃 CRF（只有码率/量化档）；③`--segments`/音轨/`verify`
的流程都要适配「收编码分片 → `-c copy` 封装」。量具：`out/_probe/webcodecs-check.mjs`。

> 粗算：现状 133ms/帧 → (a) 约 41ms/帧（24 fps）；(b) 约 47ms/帧（21 fps）。
> 两条路都比现在快 3× 左右，而 (a) 改动小得多。

### 5.5 顺手修掉的工具问题

`anim hashes --baseline` 原来把参考帧用 `[...cur]` **展开成 830 万个数字**再经
`page.evaluate` 序列化 —— demo 的 11 帧基线实测要几分钟（常常跑超时）。改成 **base64 传参**
（页面侧 `diffToB64`）：**11 帧 8.5 秒**，结论完全不变（逐像素 max 0）。

## 6. raymarch vs 投影线段批：同一条走廊的成本对照（2026-10，BACKLOG 1-10）

`tasks/pdoom-lab` 的走廊段（`scenes/corridor.js:31`）从一开始就留着两套实现：写
`params: { impl: 'lines' }` 走**投影线段批**（第 ① 种 3D），不写就走**真 raymarch**（第 ② 种）。
同一台机器、`--only corridor`（选中段被平移到时间轴开头）、1080p、`samples=auto`、快门 0.5：

| 实现 | 帧率 | ms/帧 | 该段（450 帧 / 7.5s）预估 | 整片（1920 帧）预估 |
|---|---|---|---|---|
| **raymarch**（默认） | **0.83 fps** | 1214 ms | 9.1 分钟 | 30.9 分钟 |
| **线段批** | **1.26 fps** | 796 ms | 6.0 分钟 | 28.9 分钟 |
| 比值 | **1.52×** | | | **1.07×** |

```sh
node scripts/anim.mjs video pdoom-lab --dry-run --only corridor     # raymarch（默认）
# 再把 corridor 那段临时改成 params: { impl: 'lines' }，跑同一条命令；跑完 git checkout 恢复。
# dry-run 只测速、不出片、不写基线 —— 所以"改了再改回来"对 out/pdoom-lab/hashes.json 零影响。
```

⚠ **两个必须一起读的注意**（否则数字会被读成错的结论）：

1. **整片口径只差 1.07×** —— 因为走廊段只占 `7.5 / 32 ≈ 23%`，其余四段本来就是解析投影 / 线段批做的。
   拿整片数字去说"raymarch 不贵"是错的：**要比就比同一条走廊（1.52×）**。
2. **两种实现的画面本来就不同**：raymarch 那一版有**软阴影、AO 与雕刻排线**，线段批是**纯线框**。
   所以这不是"同样的画面快 1.52×"，而是"**便宜的那一版少给了这些**"。
   选哪一种按「画面需要什么」（`AGENTS.md` §5.5 那张表），**不是**按这个数字。

## 7. 出片路径的两个"以前没量过"的开关（2026-10-16，BACKLOG 头部 ⑧）

> 两条都是**实测**，起因是 BACKLOG 里那两条"只接了线、没验过"的遗留：
> `--scan-nf` 的 4K 代价（旧注释写"4K = 4×，未实测"）与 `--parallel`（只接了线、**一次都没跑过**）。

### 7.1 `--scan-nf`：单次扫描的代价随像素数**线性**涨（4K = 4.0×，外推成立）

夹具：`tasks/_style-sampler`（配置档、无音频、纯 shader 背景），`shot --from 0 --to 2`、
`samples=1`、120 帧、同一台机器（5800H + 核显）。**只改 `--scan-nf` 一个变量**：

| 分辨率 | `--scan-nf 0` | `--scan-nf 1`（每帧都扫） | 单次扫描代价 |
|---|---|---|---|
| 1080p | 9.9s — **12.1 fps**（82.6 ms/帧） | 14.5s — **8.3 fps**（120.5 ms/帧） | **+38 ms** |
| **4K**（`--scale 2`） | 33.5s — **3.6 fps**（279 ms/帧） | 51.7s — **2.3 fps**（431 ms/帧） | **+152 ms** |

- 比值 **152 / 38 = 4.0×**，与"浮点回读的像素数 ×4"一致 ⇒ 旧注释那句
  "代价随像素数线性涨（4K = 4×，未实测）"现在**有实测了**。
- **默认档（每 30 帧扫一次）摊薄之后**：1080p +1.3 ms/帧（当年实测 +0.35%）；
  4K **+5.1 ms/帧 = +1.8%**（279 ms 的底）⇒ 默认开着的决定在 4K 下依然成立。
- `--scan-nf 1`（每帧都扫）在 4K 下是 **+55%** 帧时间 —— 只适合几秒的片段，不要拿它出片。

### 7.2 `--parallel 2`：**第一次真跑**（1020 帧 / 17s，实测 1.75×）

```sh
node scripts/anim.mjs video _style-sampler --parallel 2
# ✓ 1020 帧（4 段并行拼接，ffprobe 复核通过），用时 508.8s
```

四段各自的速度（`out/_style-sampler/_style-sampler.par/p0*.log`）：

| 段 | 帧数 | 用时 | 速度 |
|---|---|---|---|
| p00 0.00–4.40s | 264 | 216.1s | 1.2 fps |
| p01 4.40–9.60s | 312 | 258.6s | 1.2 fps |
| p02 9.60–13.60s | 240 | 228.9s | 1.0 fps |
| p03 13.60–17.00s | 204 | 183.7s | 1.1 fps |

- 四段工作量合计 **887.3s**，墙钟 **508.8s** ⇒ **1.75×**（2 进程）。
  与历史结论"2 进程 1.81×"一致 —— 也就是**它真的并行起来了**（不是串行排队）。
- ⚠ 这**不代表**"多进程是免费加速"：NV12 之后 4 进程实测反而慢于单进程（§2 ②）。
  `--parallel` 至今仍**静默忽略 `--segments`**、只转发部分参数（BACKLOG 1-24 那一条**没做**）。
- 每段都是 **24 子帧**（`samples=auto`）—— 这个任务的自适应采样一直吃满 24 档，
  所以绝对帧率低（1.0–1.2 fps）；比并行收益要拿**同一份工作量**比，别跟 `samples=1` 的读数混。


### 5.7 出片码率：crf16 + tune grain 在带颗粒的画面上的实测（2026-10-26）

触发场景：准备出片时量了一支 2 秒的 demo（1080p60，`--samples 1`），**55.6 MB / 233 Mbit/s**。
按这个比例，75 秒的片子 ≈ 2 GB —— 上传慢、平台还要再压一遍（二次损失）。所以实测了几档：

| 参数 | 2 秒文件 | 码率 | SSIM(Y) vs 未封顶 |
|---|---|---|---|
| 默认（`-crf 16 -tune grain`） | 55.6 MB | 233 Mbit/s | 基准 |
| `--crf 20` | 55.6 MB | 233 Mbit/s | —（**几乎不动**：颗粒保护把细节全留下了） |
| `--crf 18` | 65.5 MB | 275 Mbit/s | —（同上，crf 不是这里的旋钮） |
| `--bitrate 25M` | 10.4 MB | ≈42 Mbit/s 实测 | **0.671** |
| `--bitrate 12M` | 4.9 MB | ≈20 Mbit/s 实测 | **0.578** |
| `--vcodec h264_mf`（显式 12M） | 20 MB | 84 Mbit/s | 未量 |

**读法**：

- **`--crf` 在这种画面上没用**，因为 `-tune grain` 的目标就是保住噪点，crf 一动体积几乎不变；
  要控体积只能用 `--bitrate`（2026-10-26 起 x264 路径也认它，走「封顶 VBR」：`-b:v` + `-maxrate 1.4×` + `-bufsize 2×`）。
- **SSIM 0.58 / 0.67 都很低**（Y 通道），说明这段画面的颗粒本身就在高频，压到 12–25 Mbps 是**能看出来**的损失。
  带重颗粒的片子交付时建议 `--bitrate 40M` 以上，或者干脆**不用 `-tune grain`**（把颗粒交给平台的编码器，让它在更高码率下自己决定）。
- 这不影响"引擎出片"的正确性（默认行为一个字节没变），只是**交付前要量一次体积**：
  `node scripts/anim.mjs video <任务> --dry-run` 看帧数，然后按 `秒数 × 码率 / 8` 估体积。
