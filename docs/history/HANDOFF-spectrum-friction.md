## 1. A：自适应运动模糊在静止画面上不收敛（最贵的一条）

### 现象

`node scripts/anim.mjs video spectrum` 实测 **0.9 fps**，4550 帧要 ~85 分钟。
而同一支片子 `perf --samples 1` 是 **67.5ms/帧（14.8 fps）**。

### 根因（已核实到代码，不是猜的）

`src/core/engine.js:704-757` 的自适应循环：先渲染 `BASE_SAMPLES` 组，再三级三倍地加（8 → 24 → 72 → 216），
每级算一次 `_sampleError()`（`engine.js:890`），`err < tol` 才停。

我一开始以为是**颗粒**（每帧换种子）导致的——**这个猜测是错的**，而且值得记下来：
`engine.js:783` 是 `this.post.render(..., frameSeed(idx))`，种子来自**帧号**，
同一帧的所有子帧种子完全相同；而且子帧累加发生在**后处理之前**。颗粒不会进 `_sampleError()`。

真正的原因是：**`makeShot` 让摄影机抖动跟着子帧时间走**。
`src/kit/shot.js:79` 是 `return cameraPost(ctx.f.t, post)`，而 `ctx.f.t` 在子帧路径里是
**子帧时刻**（`engine.js:460` 的 `_ctxFor(item, t, …)` 里 `t` 就是 `subT`）。
`cameraPost` 里带 `shake: shakeSmooth(f.t, …)`（`src/core/cam.js:307`）——
于是同一帧的 8 个子帧**各自抖在不同的位置**，`_sampleError()` 永远差那么一点。

对一支"画面主体是静止图表"的片子，这等于把每帧都当成甩镜来做运动模糊。

### 当时的绕法

段上写 `maxSamples: 8`（时间线字段，见 `AGENTS.md` §3.2）：实测 **2.5 fps**，分块实际 31 分钟。
代价是运动段的拖影比 24/72 子帧粗——对这支片子可接受（运动只在入场那 2–3 秒）。

### 建议的修法（**没做**，留给下一轮拍板）

三条，从便宜到贵：

1. **别让摄影机抖动进子帧误差**：`_sampleError()` 比较前先把 `shake`/`zoom` 以外的东西对齐——
   这一条改动小但要小心（抖动本来就是"该被模糊掉"的东西，全排除会让甩镜采样不足）。
2. **给自适应加"收敛停滞"熔断**：连续两级 `err` 下降不到 X% 就停，并把这个读数打进 `--json`。
   现在没有任何办法知道"它为什么一直在加"，作者只能靠实测帧率反推。
3. **让 `perf` 报子帧分布**：现在 `perf` 只量 `samples=1`，而成片走的是 `auto`。
   作者要预估时长必须先自己发现这件事（我就是跑了两次才知道）。

## 2. B：整片渲染中途卡死

### 现象

`video spectrum`（不分块）跑到 **1260/4550 帧**后：日志 12 分钟无新增、
`out/spectrum/spectrum.mp4` 的 mtime 不动、推流积压从 26MB 涨到 **382MB**。
进程还活着（`tasklist` 有），但不推进。

### 当时的绕法

杀进程 → `video spectrum --segments 10` → 10 块全部完成（每块 ffprobe 复核通过），总 1859.5s。

### 观察（没有定性，只记事实）

- 卡死点在 **1260 帧 = 21.0s**，正好是第 2 段中间（`series` 段 9.17–25.0s）。
- 分块渲染时，第 2 段所在块（第 3 块 19.00–25.00s）**顺利通过**，所以不是内容导致的必然崩溃。
- 更像是长时间单进程推流的累积问题（内存/ws 缓冲）。分块每块重启一次浏览器，天然规避。

**建议**：把 `--segments` 变成长片子的默认建议值并写进 `AGENTS.md` §7 的 `video` 那一行
（现在它是作为"可选优化"介绍的）。另外渲染卡死时 CLI **没有任何超时/心跳告警**，
只有人盯着日志才发现——加一条"N 秒没有新帧就打印一次警告"会省掉很多盯屏时间。

## 3. C：`--only` 平移段到时间轴开头

`AGENTS.md` §7 写了这条（"⚠ `--only` 把选中的段**平移到时间轴开头**，所以 `-t` 是段内时间"），
**我仍然踩了两次**：一次以为场景坏了（出图全黑），一次以为 `series2` 没画东西。

低成本改进：`--only` 生效时在输出里多打一行
`· --only 已启用：-t 按段内时间解释（你给的 10.6s 落在段外 → 全黑）`，
尤其是 `-t` 超出该段时长时**直接报错**而不是渲一张黑图。

## 5. E：响度只有读数、没有官方"贴靶子"的做法

`anim mix` 实测 **-21.2 LUFS**，离平台靶子 -14 差 7.2 LU。引擎的立场是**只报不归一化**
（`scripts/lib/mix.mjs:216`，理由充分：归一化会让所有已交付片子音轨重出）。

这没问题，但**没有任何地方告诉你"那我该怎么做"**。我最后写了
`scripts/master-spectrum-audio.mjs`（loudnorm 两遍式，-21.2 → -14.0 LUFS / -0.89 dBTP）。

建议：把"贴靶子的标准做法"写进 `docs/NARRATION.md` 或 `AGENTS.md` §6.5，
或者干脆给 `anim mix` 加一个**显式**的 `--target -14`（默认关，开了才归一化）。
后者更好：这是"每支新片子都要做一遍"的动作，不该每支片子重写一个脚本。

另外一条小的：配乐床比片子短时 `mix` 只警告一句（"后面 3.33s 会没有音乐"），
我第一版就是这样发的——**警告在滚动的日志里很容易漏看**。

## 6. F：版面守门的 focus 对"主体是图形"的段不友好

我的每一段主体都是**图形**（方波、格阵、波形），文字只是标注。
但版面守门报的读数一直是"主体区 0 块"——因为 `focus` 里确实没有**文字块**。
这不会报错（判据 ③ 只对声明了 focus 的段跑"主体区压了几块字"），
但会让"主体区 0 块"看起来像"没画东西"。

真正卡住我的是**判据 ②（主体之外 ≤ 2 个看的地方）**：我的 `sound` 段有
`SIGNAL / 03` + `声音` + `波形` + `频谱` + `LOW` + `MID` + `HIGH` 七个文字入口，
哪怕观众一眼就知道主体是波形，判据也会数成 5 块、3 个"看的地方"。
解决方式是**把标签合并成一行**（`波形 2.4 s　·　LOW / MID / HIGH　·　…`）——
这个改法本身是对的（纪律 3"读数一次只揭一个"），但**文档里没有"标注可以合并成一行"这个招**，
我是试出来的。建议 `docs/LAYOUT.md` §1 加一句。

## 7. G：节奏腿是对的（记一笔免得下次又抱怨）

`check` 报"节奏 CoV 0.15 < 0.25 —— 节拍器"。我第一反应是"这判据是不是太严"，
但按它的建议加了一记 3.4 秒纯视觉短击后，CoV 0.31，而且**片子确实更好看了**
（长枪段之间有了呼吸）。这条判据应当保留，只是它的措辞可以更直接一点：
现在只说"匀速镜头长度在观众眼里就是一格一格翻灯片"，没说"那就加一记短击"。
